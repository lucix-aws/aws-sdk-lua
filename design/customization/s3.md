# S3 Customizations

S3 is the most heavily customized AWS service. This document catalogs all
S3-specific behaviors that differ from standard SDK operation flow, organized
by implementation priority.

## Current State

**Working:**
- S3 error XML format (`no_error_wrapping = true` on restxml protocol)
- Endpoint rules resolve correctly (virtual-host URL, path-style URL)
- `disableDoubleEncoding` extracted from endpoint auth schemes into signer properties
- Signing name/region overrides from endpoint auth schemes

**Broken:**
- Bucket appears twice in URL (serialized path + endpoint hostname)
- Signer ignores `disable_double_encoding` property (always double-encodes)
- No 200-error handling
- No Content-MD5 for required operations
- No unsigned payload for streaming
- No S3-specific error metadata (HostID)

---

## Tier 1: Blocking (S3 is broken without these)

### 1. Remove `{Bucket}/` from serialized HTTP paths

**Problem:** The serialized `http_path` includes `/{Bucket}/{Key+}`. The
endpoint rules already place the bucket in the correct location (hostname for
virtual-host, URL path for path-style). Result: bucket appears twice.

```
Endpoint URL: https://my-bucket.s3.us-east-1.amazonaws.com
Serialized path: /my-bucket/hello.txt
Combined: https://my-bucket.s3.us-east-1.amazonaws.com/my-bucket/hello.txt  ← WRONG
```

**Fix:** Codegen customization (Java) that strips `{Bucket}/?` from all S3
operation HTTP URI patterns before code generation. This is exactly what the Go
SDK does (`S3HttpPathBucketFilterIntegration`).

**Where:** `aws-sdk-lua/codegen/` — S3-specific `GoIntegration` equivalent
that transforms `HttpTrait` URIs.

**Fastest hackathon alternative:** Runtime interceptor on the S3 client that
strips the first path segment when the endpoint URL contains the bucket as a
subdomain. Less correct (doesn't handle path-style properly) but unblocks
immediately.

### 2. Respect `disable_double_encoding` in the signer

**Problem:** S3's endpoint auth schemes return `disableDoubleEncoding = true`.
The auth module extracts this into `signer_properties.disable_double_encoding`.
The signer's `canonical_path` function ignores it and always re-encodes path
segments. This produces invalid signatures for keys with special characters.

**Fix:** Pass `props` to `canonical_path`. When
`props.disable_double_encoding` is true, use the path segments as-is (they're
already encoded by the protocol serializer).

**Where:** `smithy-lua/runtime/smithy/signer.lua`

## Tier 2: Correctness (S3 works but has bugs without these)

### 3. 200-error handling

**Problem:** `CopyObject`, `CompleteMultipartUpload`, and `UploadPartCopy` can
return HTTP 200 with an `<Error>` XML body. The SDK currently treats these as
successful responses.

**Fix:** An S3-specific interceptor (or per-operation plugin) that checks if a
2xx response body starts with `<Error>` root element. If so, deserialize as an
error. Per the SEP:
- `SlowDown` or `InternalError` → treat as 5xx (retryable)
- Any other code → treat as unknown error
- Must NOT hard-code operation list — should be driven by model traits
- Must NOT fail if XML parsing fails — fall through to normal handling
- Must NOT apply to streaming blob or streaming union responses

**Where:** `smithy-lua/runtime/smithy/protocol/` or an S3 interceptor.

**Affected operations:** CopyObject, CompleteMultipartUpload, UploadPartCopy.

### 4. S3-specific error metadata (HostID + RequestID)

**Problem:** S3 returns `x-amz-request-id` and `x-amz-id-2` on every
response. These are critical for AWS support troubleshooting. Currently not
extracted.

**Fix:** Enrich error tables with `request_id` and `host_id` fields from
response headers. Could be done in the restxml protocol (when
`no_error_wrapping` is set) or as an S3 interceptor.

**Where:** S3 client interceptor or protocol extension.

### 5. Content-MD5 for `httpChecksumRequired` operations

**Problem:** ~20 S3 operations (DeleteObjects, PutBucketCors, PutBucketPolicy,
PutBucketLifecycle, etc.) require a `Content-MD5` header. The SDK doesn't
compute it.

**Fix:** Runtime module that computes MD5 of the request body and sets the
`Content-MD5` header (base64-encoded). Driven by a trait flag in the operation
schema (or a per-operation property).

**Dependency:** Pure Lua MD5 implementation (~100 lines).

**Where:** `smithy-lua/runtime/smithy/checksum.lua` or similar.

### 6. Unsigned payload for streaming operations

**Problem:** PutObject and other upload operations currently have the signer
read the entire body into memory to compute SHA-256. For large uploads this
causes OOM and is extremely slow. Over HTTPS, S3 allows `UNSIGNED-PAYLOAD`.

**Fix:** Add a signer property (e.g., `unsigned_payload` or
`payload_signing_mode`) that, when set, uses `UNSIGNED-PAYLOAD` as the
`x-amz-content-sha256` value instead of computing the hash. The Go SDK calls
this "dynamic payload signing" — unsigned over HTTPS, signed over HTTP.

**Where:** `smithy-lua/runtime/smithy/signer.lua` — check property before
reading body.

**Driven by:** Per-operation trait (`@auth([sigv4: { unsignedPayload: true }])`)
or a codegen-emitted property.

## Tier 3: Important but not blocking basic operations

### 7. `ForcePathStyle` client option

**Problem:** Users need path-style addressing for S3-compatible services
(MinIO, LocalStack) or buckets with dots.

**Fix:** Wire `cfg.force_path_style` through to endpoint params as
`ForcePathStyle`. The endpoint rules already support this parameter.

**Where:** S3 client constructor in `aws-sdk-lua/service/s3/client.lua`.

### 8. 100-continue for large uploads

**Problem:** Large PUT requests should use `Expect: 100-continue` to avoid
sending the full body before the server confirms acceptance.

**Fix:** Add `Expect: 100-continue` header when Content-Length ≥ threshold
(default 2MB) for PUT requests (PutObject, UploadPart).

**Where:** Interceptor (`modify_before_transmit`) or protocol hook.

### 9. GetBucketLocation custom deserialization

**Problem:** GetBucketLocation returns `<LocationConstraint>region</LocationConstraint>`
as the root element with no operation wrapper. Most other operations wrap in an
operation-specific element.

**Status:** May already work — the schema has `XML_NAME = "LocationConstraint"`
on the output structure. Needs testing.

**Where:** Test first. If broken, needs a custom deserializer or schema
adjustment.

### 10. Expires header graceful parsing

**Problem:** S3's `Expires` header often contains non-standard timestamp
values. The SDK should not fail the entire request if parsing fails.

**Fix per SEP:**
- Do not fail the request if `Expires` parsing fails
- Log a warning, leave the field nil
- Generate a synthetic `ExpiresString` member with the raw unparsed value
- Deprecate the typed `Expires` field

**Where:** Codegen (add ExpiresString member) + runtime (lenient timestamp
parsing).

### 11. IsTruncated pagination

**Problem:** S3 paginators should check `IsTruncated` as a "more results"
indicator. Without it, the paginator may make one extra API call when the token
is present but `IsTruncated = false`.

**Fix:** Add `more_results` field to paginator config. The paginator runtime
checks this field — if it's `false`, stop even if a token is present.

**Where:** `smithy-lua/runtime/smithy/paginator.lua` + codegen for S3
paginators.

## Tier 4: Stretch / Not needed for hackathon

### 12. S3Express support

Custom auth scheme (`com.amazonaws.s3#sigv4express`), CRC32 default checksums,
`CreateSession` credential provider with LRU cache, `x-amz-s3session-token`
header instead of `x-amz-security-token`. Major effort.

### 13. Flexible checksums v2

CRC32, CRC32C, CRC64-NVME, SHA-256, SHA-1 request/response checksums.
`aws-chunked` transfer encoding with trailing checksums. Significant effort.

### 14. ARN-based resources — NOT NEEDED

Access Points, Object Lambda, Outposts, MRAP are fully handled by endpoint
rules. The Go SDK's `processARNResource` / `updateEndpoint` middleware is
legacy from before endpoint rules existed. Our SDK was built with endpoint
rules from day one — the ruleset parses ARNs, constructs the correct URL, and
returns the correct `authSchemes` (signing name, region, region set). No
additional runtime work needed.

### 15. Endpoint-driven auth scheme selection

**Problem:** The standard pipeline flow is: resolve auth scheme (from
operation model) → resolve endpoint → apply endpoint property overrides to
signer properties (signing name, region). This works for most services because
the endpoint only *adjusts* the already-selected scheme.

S3 is different. For Multi-Region Access Points, the endpoint rules return
`sigv4a` as the auth scheme — a completely different signer, not just a
property tweak on sigv4. The current override mechanism can't swap the scheme
itself, only adjust properties on the one already selected.

S3 and EventBridge are the only two services where endpoint rules *determine*
the auth scheme rather than just coloring it.

**Fix:** The S3 client needs a custom auth scheme resolver that defers to
endpoint resolution:

1. Resolve the endpoint
2. If the endpoint returns `properties.authSchemes`, use those as the auth
   scheme options (mapping `sigv4a` → `aws.auth#sigv4a`, `sigv4` →
   `aws.auth#sigv4`, `sigv4-s3express` → `com.amazonaws.s3#sigv4express`)
3. Fall back to the operation's `effective_auth_schemes` only if the endpoint
   doesn't specify

This requires either:
- Reordering the pipeline for S3 (endpoint resolution before auth selection), or
- A two-pass approach where auth is re-resolved after endpoint resolution when
  the endpoint carries auth scheme information

The Go SDK implements this as `endpointAuthResolver` — a custom auth scheme
resolver registered on the S3 client that merges endpoint-derived auth options
with modeled defaults, giving the endpoint's choice priority.

**Where:** S3 client constructor registers a custom `auth_scheme_resolver` that
has access to the endpoint resolver. The `sigv4a` auth scheme must also be
registered in `cfg.auth_schemes`.

**Dependency:** `sigv4a.lua` already exists and works. Just needs to be
registered as an available auth scheme on the S3 client.

### 16. Transfer acceleration

Endpoint rules support the `Accelerate` parameter. Just needs client config
wiring (`cfg.use_accelerate` → `ep_params.Accelerate`).

### 17. Presigned URLs

Entire presigning subsystem doesn't exist. Requires query-string-based signing
(credentials, date, expires, signature all in URL params instead of headers).

### 18. aws-chunked transfer encoding

For streaming checksums — body is re-encoded as `aws-chunked` with the
checksum in a trailing chunk. Complex interaction with Content-Length,
`x-amz-decoded-content-length`, and the transport layer.

## Recommended Execution Order

| # | Item | Effort | Impact |
|---|------|--------|--------|
| 1 | Remove bucket from path (codegen or hack) | 30min | Unblocks all S3 ops |
| 2 | Disable double encoding in signer | 15min | Fixes signing for special chars |
| 3 | Unsigned payload | 30min | Prevents OOM on uploads |
| 4 | ForcePathStyle option | 5min | Useful for testing |
| 5 | Error metadata (HostID) | 15min | Improves debugging |
| 6 | 200-error handling | 45min | Prevents silent corruption |
| 7 | Content-MD5 | 1hr | Unblocks ~20 operations |
| 8 | 100-continue | 15min | Performance for uploads |

Items 1–2 together make the S3 example work. Item 3 makes uploads viable.
Items 4–8 round out correctness for a demo.
